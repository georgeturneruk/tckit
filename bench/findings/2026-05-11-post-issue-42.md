# 2026-05-11 — Post-#42: reader cache, mtime guard, refocused task set

Third pass of the harness. Bundles the #42 reader-cache fix with a `.plcproj` mtime guard, parks the find-callers task, and adds two new reading-focused tasks (`02-pinpoint-method`, `03-explain-fb-api`). Same target project (TcUnit), same model (Opus 4.7), native TcKit on Windows, N=1.

## What changed since the post-impl bench

1. **Issue #42 fixed.** `TcKitConfig.reader()` now caches a single `XmlReader` for the server's lifetime, so the file-name index populated by `get_structure` survives across MCP requests. Confirmed in this bench by Task 01's three `get_pou_interface` follow-ups returning interface data (vs the previous run where they silently `FileNotFoundError`'d).
2. **`.plcproj` mtime guard added** alongside the cache fix. The reader records the `.plcproj` mtime when it builds the index; subsequent reads `stat()` and rebuild on change. Covers TcKit-driven structural writes and external edits (XAE Shell, git, manual). Design rationale in ADR-0004.
3. **Task B (`02-find-callers.md`) parked.** TcKit has no purpose-fit find-callers tool (ADR-0001 explored that and recommended deferral); both configs default to `Grep` and the bench learns nothing.
4. **Two new reading tasks.** `02-pinpoint-method` reads a single method body (`FB_TestSuite.AssertEquals_INT`). `03-explain-fb-api` summarises an FB's public API from declarations only.
5. **`tc-read-project` skill** got the same "When TcKit is unavailable" fallback section that `tc-orient-project` already had, so vanilla can follow the layered read pattern with stock tools instead of refusing.

## Setup

- **Target:** TcUnit at `C:/TcUnit`.
- **Configs:** `empty` (vanilla Claude Code) and `tckit` (TcKit SSE on `http://localhost:8000/sse`).

- **Model:** Opus 4.7.

## Findings

### 1. #42 unblocks the orient chain, but the 1.5x token target was a Docker-era artefact

The post-impl bench predicted that fixing #42 would push Task 01's TcKit-vs-vanilla token ratio past 1.5x, because two failed `get_pou_interface` follow-ups would start returning real data. After the fix:

- **The chain works.** TcKit's three interface reads on Task 01 now return real declarations; the orientation report cites real method signatures rather than papering over the gap with `get_structure` data alone.
- **The token ratio came in at 0.99x, not 1.5x.** TcKit went from 3,954 tokens (post-impl, with broken follow-ups) to 4,627 (post-#42, with working follow-ups). Vanilla improved further too as the skill's fallback path settled in. On a project this small, the skill is doing most of the work and the marginal TcKit-vs-vanilla gap is narrow.

The 1.5x target was set against a TcKit number that included three failing requests. With the bug fixed the number went *up* (more real data acquired) and the comparator (vanilla) also got better. The orientation is qualitatively richer on TcKit; the token-economy headline is a tie. Both true.

### 2. Task 03 surfaced a real behaviour bug: writer-tool failures can derail reader-tool selection

`03-explain-fb-api` was designed as `get_pou_interface`'s home turf: one call returns every method's signature. TcKit instead reached for `open_project` (writer adapter, needs the Windows bridge service), got `bridge not reachable`, and abandoned all TcKit tools for the rest of the task — falling back to `Glob`/`Grep`/`Read` against the raw `.TcPOU` XML.

This is a model-behaviour failure, not an infrastructure failure: the reader tools were available the whole time. The skill's `allowed-tools` list and description did not steer the model away from `open_project` for an "explain this FB" prompt, and one writer-side error generalised in the model's head to "TcKit isn't working".

Two fix levers, both for a follow-up PR:

- **Skill wording.** `tc-read-project`'s description and procedure should call out that reader tools (`get_structure`, `get_pou_interface`, `get_pou_item`, `get_gvl`, `get_dut`) work without the bridge and a writer-side error doesn't affect them.
- **Skill `allowed-tools` scope.** Reading skills probably should not list writer tools at all, so the model can't reach for `open_project` mid-read.

TcKit still came out ahead on tool calls (10 vs 24) and wall (114s vs 152s) on Task 03 even after the derail, because once it switched to stock tools it did a tighter version of what vanilla did. Tokens nudged slightly in vanilla's favour (8,430 vs 8,829) because TcKit's failed `open_project` plus extra Glob added overhead.

### 3. Pinpoint reads are the cleanest TcKit win on this task set

`02-pinpoint-method` is the one task where TcKit's single-purpose `get_pou_item` call has no real stock-tool equivalent. Result: TcKit ratio 1.23x tokens, 1.33x wall, 1.33x tool calls — modest in absolute terms only because the task is small (1.4-1.7k tokens, 20-30s). This is a *leading indicator* for ADR-0003's patch-style writes: the same "fetch only the method you need" win will compound when the edit path requires read-before-write.

### 4. The mtime guard is silent and that is correct

The bench did not exercise structural changes, so the mtime guard's hot path is just an extra `stat()` per read. Unit tests in `tests/integration/test_xml_reader.py` cover the rebuild path (touch `.plcproj`, observe a new POU being discovered) and the warm path (touch a `.TcPOU` body, observe no rebuild). No observable bench impact, which is what we want.

## What this validates and invalidates

**Validates:**

- The #42 fix itself: the layered read pattern composes across MCP requests now. The Task 01 chain is the proof.
- ADR-0004's choice of `.plcproj` mtime as the staleness signal: the guard does not interfere with normal reads and the rebuild path is exercisable.
- Task 02 as a benchmarking shape: a pinpoint read is short enough to be cheap, narrow enough to give TcKit a real edge, and predictive of write-path savings.

**Refines:**

- The 1.5x token target from the post-impl write-up was framed around fixing a measurement bug, not a TcKit capability gain. The orient ratio is around 1.0x on a project this small, and that is probably honest: small projects let the skill carry vanilla almost as far as TcKit. A larger project (TwinCAT/TcOpen TcoCore, ~200+ POUs) is where the gap should widen.

**Open:**

- The reader-skill / writer-tool collision on Task 03. Filing as a separate issue rather than fixing in this PR; the fix needs its own re-bench to verify.

## Caveats

- N=1. Token deltas under ~10% should not be treated as signal.
- One model (Opus 4.7). A Haiku 4.5 sweep is on the next-experiments list.
- One project (TcUnit, ~50 POUs). The post-impl bench called this out and it is still the binding caveat for "TcKit's win is small".
- TcKit ran native, not Docker. #43 still blocks Docker bench parity.

## Suggested next experiments

1. **Re-bench Task 03 after the reader-skill scope fix.** Predicted: TcKit reaches `get_pou_interface`, drops to ~3 calls and a clean win.
2. **N=3 on the three-task set** once the skill fix lands. Stable means and tighter ratio confidence at low cost.
3. **Larger project bench (TcOpen TcoCore).** This task set on a ~200-POU project should widen the gap, because the stock-tool side scales worse than TcKit's index lookup.
4. **Haiku 4.5 sweep on the same three tasks.** Tests whether a smaller model follows the skill's directive flow more literally.
5. **ADR-0003 (patch-style writes) re-bench** once it ships. Task 02's win is the leading indicator; the write equivalent should be larger.

## Interpretation, in one line

**The #42 fix made the orient chain real, the mtime guard makes the new long-lived cache safe, and the refocused task set reveals where TcKit's edge lives today (pinpoint reads) and where it gets derailed by a stale skill description (FB API summaries via the writer tool).** Headline target unmet at N=1 on a small project; bench is now exercising the parts of TcKit worth optimising.
