# 2026-05-11 - Post-ADR-0002: orient skill + extended get_structure

Second run of the harness, after shipping ADR-0002 (extended `get_structure` with tasks, libraries, and folder grouping; new `tc-orient-project` skill). Same benchmark setup as the 2026-05-11 baseline so the deltas are directly comparable.

## What changed since the baseline

1. `ProjectReader.get_structure` now returns `TaskInfo` (cycle in microseconds, priority, bound programs), `LibraryRef` items, and a `folder` per `POURef`. Adapters (just `XmlReader` today) read `.plcproj`, `.tsproj`, and `.TcTTO` to populate them.
2. New skill `tc-orient-project` codifies a budgeted first-touch flow: one `get_structure`, sample one FB per subsystem, stop. Includes an explicit fallback for when TcKit MCP tools are not registered (read the small project-shaping XML files directly).
3. `tc-read-project` description tightened to "follow-up reads after orientation".
4. `get_structure` tool docstring rewritten so the model sees that one call now covers subsystems, tasks, libraries, GVLs, DUTs.

## Setup

- **Target project:** TcUnit at `C:/TcUnit`.
- **Configs:**
    - `empty` - vanilla Claude Code, built-in tools only.
    - `tckit` - TcKit on SSE via `http://localhost:8000/sse`.
- **TcKit transport:** changed from Docker to **native Windows** (Python 3.11 venv at `.venv-bench/`, `python -m tckit.server --transport sse`). The baseline ran TcKit in Docker, which silently failed every MCP call because the Linux container could not see `C:/TcUnit`. Fix tracked as [#43](https://github.com/georgeturneruk/tckit/issues/43). Native mode is the realistic Windows-user setup and the comparison is now meaningful.
- **Tasks:** `01-orient`, `02-find-callers`. Same prompts as the baseline.
- **Model:** Opus 4.7.
- **Runs:** 1 per (task, config) pair. **N=1, directional only.**

Pairwise ratios for the post-impl runs (vanilla / tckit; >1 means TcKit more efficient):

- Tokens: **1.24x** (TcKit ahead).
- Wall: **1.30x** (TcKit faster).
- Calls: 6 / 5 (TcKit slightly fewer).

Versus the baseline of 0.87x tokens (TcKit worse), the trajectory is clearly in the right direction. The 1.5x target from the baseline write-up is not met at N=1, but two known issues hold the number back; see below.

## Tool breakdown - Task A

- **empty (post-impl):** `Skill x1`, `ToolSearch x1`, `Glob x1`, `Read x3` (6 calls).
  - The orient skill loaded. Vanilla followed the new fallback path: glob for the project-shaping files, read `.plcproj` + `.tsproj` + a representative `.TcPOU` to learn conventions. Clean, disciplined exploration. No mass `.TcPOU` crawl.
- **tckit (post-impl):** `Skill x1`, `ToolSearch x1`, `mcp__tckit__get_structure x1`, `mcp__tckit__get_pou_interface x2` (5 calls).
  - The orient skill loaded. Single `get_structure` lifted all the structural data; the model then sampled two FB interfaces.

Side-by-side with the baseline:
- Baseline empty: `Bash x11, Read x6, Skill x1, ToolSearch x6` (24 calls). Mass exploration via stock tools.
- Baseline tckit: `Bash x9, Read x9, Grep x3, Glob x1, PowerShell x2, Skill x1, ToolSearch x1, get_structure x4` (30 calls). All four `get_structure` calls returned `Project path not found` because of the Docker path issue.

The directive skill collapses the 24-call vanilla flow to 6, and the 30-call TcKit flow to 5. **Direction (skill + tool description) beats more tools.**

## Findings

### 1. The skill is the lever, the tools are the foothold

The biggest finding from the baseline was "tool availability is not tool adoption". This run is the natural counter-experiment: a directive skill turns the same `get_structure` call into a 5-call orientation. Both configs *also* improved when the skill loaded - vanilla's call count fell from 24 to 6 just from following the new fallback flow. Skills shape behaviour even when the headline tools are absent.

### 2. The vanilla win was unexpected and is worth understanding

Vanilla went from 8,549 to 4,893 tokens (1.75x cheaper) purely from skill direction. That is bigger than the TcKit-vs-vanilla delta in this run (1.24x). What this says about the project: when the model has a budgeted plan it can execute against stock tools, it can be very efficient on small projects. TcKit's marginal advantage shrinks accordingly. The bigger TcKit wins probably live on projects too large to glob-and-read with discipline.

### 3. Two known bugs hold TcKit's number back

While running the bench, two issues surfaced and were filed:

- **[#42](https://github.com/georgeturneruk/tckit/issues/42) - `XmlReader` is not stateful across MCP requests.** `cfg.reader()` returns a fresh adapter every request, so the `_file_index` populated by `get_structure` is gone by the time `get_pou_interface` runs. In the Task A run, both `get_pou_interface` calls failed with `FileNotFoundError` and the model gracefully wrote the orientation from the `get_structure` payload alone. Fix is straightforward (cache the reader on the config).
- **[#43](https://github.com/georgeturneruk/tckit/issues/43) - Docker SSE mode cannot see Windows host paths.** Documented above; same hole that broke the original baseline.

Fixing #42 should bring TcKit's number further down: two follow-up interface reads that today return nothing useful would actually return interface data, deepening the orientation without adding calls.

### 4. The fallback clause in the skill was load-bearing

First draft of `tc-orient-project` listed "Using `Read` or `Grep` on `.TcPOU` files" as a flat anti-pattern. On the vanilla run that triggered an explicit refusal: "TcKit isn't loaded, so I can't follow this skill". Loosening the anti-pattern to "as a substitute *when TcKit is available*" and adding a `When TcKit is unavailable` block made vanilla follow the disciplined fallback path. Worth remembering for the other skills: directives need to handle the no-tool case explicitly or they will block work.

## What this validates and invalidates

**Validates:**

- ADR-0002's core thesis: a richer single-call structure plus a directive skill *does* change behaviour. 24 calls vs 6 calls on identical work is hard to argue with at this N.
- The architectural choice not to spin up a second port for orientation. `ProjectReader.get_structure` carrying the richer payload was the right home; one call serves everything orientation needs.

**Refines:**

- The "1.5x token target" from the baseline write-up was set against broken Docker TcKit. Against a working baseline plus a skill-improved vanilla, **TcKit-over-vanilla is 1.24x at N=1**. The headline win is **vanilla-over-old-baseline at 1.75x**, attributable to the skill alone. Setting future targets needs to account for both axes.

**Open:**

- Will fixing #42 push TcKit's number past the 1.5x line? Best guess yes, because two `get_pou_interface` follow-ups currently return nothing usable; with the fix, the model gets real interface data without spending more calls. Re-test after #42 lands.

## Caveats

- **N=1.** Same caveat as the baseline. Some of these ratios could swing 20-30% on re-run.
- **One model.** Opus 4.7 only.
- **Native TcKit, not Docker.** Today's reality for any user actually working on a TwinCAT project on Windows. Docker bench will get fairer numbers once #43 is closed.
- **Two known bugs in TcKit during the run** (#42, #43). The TcKit numbers are a floor, not a ceiling.

## Suggested next experiments

1. **Fix #42, re-run Task A.** Predicted: ratio crosses 1.5x.
2. **N=3 baseline.** Same matrix, three runs per cell, both tasks. Stable means and reveals which ratios are real vs noise.
3. **Larger project.** Try TwinCAT/TcOpen TcoCore or similar (~200+ POUs) where the TcKit advantage should widen.
4. **Haiku 4.5 run.** Same matrix, smaller model. Tests whether smaller models follow declared tool patterns more literally.
5. **ADR-0003 (patch-style writes) re-bench.** Add a task that requires a one-line method-body edit. Predicted 5-10x context savings on the edit path.

## Interpretation, in one line

**With the orient skill and the richer `get_structure`, Claude collapses a 24-call mass-exploration into a 5-6 call budgeted orientation - vanilla improves 1.75x, TcKit improves 2.5x, TcKit beats vanilla by 1.24x.** The remaining gap to the 1.5x target is held back by two known bugs; closing #42 should clear it.
